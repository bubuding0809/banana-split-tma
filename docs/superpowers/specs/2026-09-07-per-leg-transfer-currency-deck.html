Per-Leg Currency
for Debt Transfers

Design spec · 2026-09-07 · banana-split-tma

approved design schema change money path

Problem

One DebtTransfer row holds one amount, one currency — shared by both groups. Debit in the source chat, credit in the target chat.

Change the currency and both groups change at once. Convert AUD→SGD in the destination and the source group silently becomes SGD too.

What that costs today

Conversion dodges the problem by skipping transfers entirely.

Transfer-only currency

Convert it → 0 rows change. Success haptic fires anyway. Balance still sits there.

Mixed currency

Expenses convert, the transfer doesn't. Group looks half-converted, no explanation.

Goal

Each group holds its own denomination.

Converting a group rewrites that group's side and nothing else.

Non-goals: rate history · undo · destination-currency choice at move time · snapshot rendering · n-way transfers

Approaches

A · Per-leg columns chosen

Four columns on DebtTransfer. Sign logic already branches on chatId — the leg picker lands in the same place. Single-table reads.

B · TransferLeg table rejected

Join on every balance read; reshapes all six readers. Buys n-way transfers, which we don't want.

C · Read-time overlay rejected

No stored legs, convert for display. Balances would drift daily; conversion stops being durable.

Data model

ColumnTypeNote
sourceAmountDecimal(12,2)leaves the source chat
sourceCurrencyString
targetAmountDecimal(12,2)arrives in the target chat
targetCurrencyString
amountdropped
currencydropped

Legs equal at creation. They diverge only via conversion.

Why drop, not mirror

Any reader still expecting a single amount fails to compile instead of silently picking a leg.

The typechecker finds the stragglers, not production.

Migration downtime accepted

One migration, one PR.

1. add 4 columns nullable
2. backfill: amount → both legs, currency → both legs
3. set NOT NULL
4. drop amount, currency

Backfill is exact — no historical rate lookups. deploy.yml migrates before deploying, so old code errors briefly.

Balance engine

Every entry point already takes a chatId to pick the sign. Now it picks the leg too.

legFor(transfer, chatId) // → { amount, currency }
// source leg when chatId === sourceChatId, target leg otherwise

Discovery · bucketing · pair queries all become leg-scoped. deleteTransfer unchanged.

A latent bug, closed

Today's predicate matches one currency against a transfer touching the chat either way.

Once legs can differ, that question has no single answer. Leg-scoped predicates make it well-formed.

Conversion

source legs: sourceChatId = chatId AND sourceCurrency = from
             → sourceAmount × rate, sourceCurrency = to

target legs: targetChatId = chatId AND targetCurrency = from
             → targetAmount × rate, targetCurrency = to

The counterpart's leg never enters the predicate. Same rate, same transaction as expenses and settlements.
